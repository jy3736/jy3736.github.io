編譯指令與練習檔相同：

gcc -std=c17 -Wall -Wextra -Wpedantic 檔名.c -o 檔名

關於訊息的文字：本講義列出的診斷訊息，是在本講義測試環境中實際編譯得到的結果。不同的編譯器或版本，訊息的用字可能不同，但通常都會包含「檔名:行:欄」和「error」或「warning」。

1. 三種問題：錯誤、警告、執行期臭蟲

用白話說

程式出問題時，第一步是分辨「是哪一種問題」，因為處理方式不一樣：

種類 什麼時候發現 會產生可執行檔嗎 例子
編譯錯誤（error） 編譯時 不會 變數名稱打錯、少了括號
編譯警告（warning） 編譯時 會，但程式可能有問題 使用還沒給值的變數
執行期臭蟲（bug） 執行時才發現結果不對 會 平均算錯、迴圈少跑一次

最麻煩的是第三種：編譯器完全不抱怨，程式也能執行，只是答案是錯的。

教材怎麼說

  • 自己寫的程式常常只有部分正確，或產生錯誤、不可靠的結果。用 -Wall 編譯有問題的程式時，編譯器會輸出診斷訊息（diagnostic）。出處：Modern C §1.2（PDF 第 17、18 頁）。
  • 除非確定程式正確，否則應該預期需要除錯；GNU C 手冊建議加上 -g 產生除錯資訊，並介紹可以用 GDB 除錯器執行程式。出處：GNU C 手冊 §2.4 Compiling the Example Program。
  • C 標準把某些程式行為歸類為未定義行為（undefined behavior），例如存取陣列範圍以外的記憶體、有號整數溢位、對空指標解參照。發生未定義行為時，程式的表現沒有任何限制；編譯器也不需要診斷它，雖然很多簡單的情況會被偵測到。出處：cppreference：Undefined behavior。

最後這一點說明了為什麼「沒有警告」不等於「沒有問題」：有些錯誤，編譯器根本不必告訴你。

對照練習

練習「單元 1」用三個小程式分別示範三種問題：漏打分號（編譯錯誤）、用 %f 讀取整數（警告）、除數忘了設定導致除以 0（執行期臭蟲）。下面各節的補充範例分別再示範不同的例子。

2. 讀懂診斷訊息

用白話說

診斷訊息看起來很嚇人，但格式其實很固定：

檔名.c:行:欄: error 或 warning: 問題描述 [-W選項名稱]

讀的時候依序看四件事：

  1. 在哪個檔案、第幾行：先跳到那一行。
  2. 是 error 還是 warning：error 一定要修；warning 通常也代表有問題。
  3. 問題描述：編譯器常常會直接建議怎麼修。
  4. 從第一則訊息開始修：一個錯誤可能引發後面一連串的訊息，修好第一個之後重新編譯，後面的常常就跟著消失了。

本節的閱讀步驟是本講義的整理方式，引用的教材中沒有直接的原文，請見文末「本講義未涵蓋的內容」。

對照練習

練習「單元 2」的基本範例用 %f 讀取整數，並逐段解讀 gcc 的警告。下面的補充範例示範另外三種常見訊息：打錯名稱、少了括號、使用未給值的變數，以及函式沒有回傳值。

補充範例 2-1：打錯變數名稱

檔名 typo.c：

#include <stdio.h>

int main(void)
{
    int total = 0;

    for (int i = 1; i <= 5; i++) {
        totl = total + i;
    }
    printf("%d\n", total);
    return 0;
}

編譯時的錯誤訊息：

typo.c:8:9: error: use of undeclared identifier 'totl'; did you mean 'total'?

一步一步看

  1. typo.c:8:9：問題在第 8 行、第 9 欄，也就是 totl 開頭的位置。
  2. error：這是錯誤，不會產生可執行檔。
  3. use of undeclared identifier 'totl'：使用了「沒有宣告過的名稱」totl。
  4. did you mean 'total'?：編譯器猜你想寫的是 total。把 totl 改成 total，重新編譯即可。

補充範例 2-2：少了一個右括號

檔名 paren.c：

#include <stdio.h>

int main(void)
{
    int score = 75;

    if ((score >= 60 && score < 80) {
        printf("中等\n");
    }
    return 0;
}

編譯時的錯誤訊息（節錄前兩行）：

paren.c:7:37: error: expected ')'
paren.c:7:8: note: to match this '('

一步一步看

  1. 第一行說第 7 行第 37 欄「預期要有 )」，第 37 欄正是 { 的位置：編譯器讀到 { 時，發現前面的括號還沒關完。
  2. 第二行是 note（補充說明），指出和它配對的左括號在第 7 行第 8 欄。
  3. 數一數：if ( 後面有兩個 (，卻只有一個 )。在 { 前面補上 ) 就修好了。
  4. 錯誤訊息指出的位置，是編譯器發現問題的地方，不一定是寫錯的地方。遇到括號、引號、大括號這類問題時，要往前找配對的符號。

補充範例 2-3：使用還沒給值的變數

檔名 uninit.c：

#include <stdio.h>

int main(void)
{
    int sum;
    int bonus = 5;

    sum = sum + bonus;
    printf("sum = %d\n", sum);
    return 0;
}

編譯時的警告訊息：

uninit.c:8:11: warning: variable 'sum' is uninitialized when used here [-Wuninitialized]

一步一步看

  1. warning：程式仍然會被編譯出來，但結果不可靠。
  2. sum 宣告時沒有給初始值，執行 sum + bonus 時，sum 裡是什麼值並不確定。
  3. GNU C 手冊說明，沒有初始值的區域變數，一開始裝的是無意義的值。在簡單的測試程式中它可能剛好是 0，但不能依賴這一點。出處：GNU C 手冊 §20.5 Local Variables。
  4. 修正方法是宣告時寫 int sum = 0;。

同樣的錯誤，換個寫法就沒有警告

檔名 uninit_loop.c：

#include <stdio.h>

int main(void)
{
    int sum;

    for (int i = 1; i <= 3; i++) {
        sum = sum + i;
    }
    printf("sum = %d\n", sum);
    return 0;
}

在本講義的測試環境中，這支程式用 -Wall -Wextra -Wpedantic 編譯，沒有出現任何警告，但它和上一支犯的是同一個錯誤：sum 沒有初始值。這正好印證第 1 節 cppreference 的說明：編譯器不需要偵測出所有問題。就算執行時剛好印出 sum = 6，程式仍然是錯的。所以不能只靠警告，宣告變數時就要養成給初始值的習慣。

補充範例 2-4：函式有一條路沒有回傳值

檔名 no_return.c：

#include <stdio.h>

int levelOf(int score);

int main(void)
{
    printf("%d\n", levelOf(85));
    return 0;
}

int levelOf(int score)
{
    if (score >= 90) {
        return 3;
    } else if (score >= 60) {
        return 2;
    } else if (score >= 0) {
        return 1;
    }
}

編譯時的警告訊息：

no_return.c:20:1: warning: non-void function does not return a value in all control paths [-Wreturn-type]

一步一步看

  1. 訊息指向第 20 行，也就是函式最後的右大括號：執行到這裡時，函式沒有 return 任何值。
  2. 什麼時候會走到這裡？當 score 是負數時，三個條件都不成立。
  3. 有回傳型別的函式如果沒有正確回傳值，呼叫端拿到的是無意義的值（GNU C 手冊 §19.5 return Statement）。
  4. 修正方法：在最後加上 return 0;，或把最後一個 else if 改成 else，確保每一條路都有回傳值。

動手改改看

  • 在補充範例 2-2 中，改成少一個 } 而不是少 )，重新編譯，看看錯誤訊息指向哪一行。
  • 補充範例 2-4 中，把 levelOf(85) 改成 levelOf(-5)，想一想為什麼不能相信它印出來的數字。

3. 重現、修正、再測試

用白話說

執行期臭蟲沒有訊息可以讀，只能靠測試發現。處理的流程是：

  1. 重現：找出一組「一定會出錯」的輸入，並寫下預期結果和實際結果。
  2. 縮小範圍：暫時在程式中加上 printf，印出中間的變數值，找出從哪一步開始不對。
  3. 修正：只改有問題的地方。
  4. 再測試：用同一組輸入確認修好了，也用原本正確的輸入確認沒有改壞別的地方。

這個流程是本講義與課程講義的整理方式；引用的教材中與它最直接相關的，是 GNU C 手冊「預期需要除錯」的提醒，以及 Beej 函式庫參考對 assert 的說明（見補充範例 3-3）。

對照練習

練習「單元 3」的基本範例處理「除數忘了設定導致除以 0」，並示範重現、修正、再測試的循環；綜合練習修正一支讀取簽到檔的程式。下面的補充範例示範兩個編譯器完全不會警告的臭蟲，以及用 assert 讓錯誤提早現形。

補充範例 3-1：平均算錯了

症狀：三次小考 80、85、88，平均應該是 84.33，程式卻印出 84.00。

檔名 avg_bug.c：

#include <stdio.h>

int main(void)
{
    int q1 = 80;
    int q2 = 85;
    int q3 = 88;

    double average = (q1 + q2 + q3) / 3;
    printf("平均：%.2f\n", average);
    return 0;
}

實際輸出：

平均：84.00

一步一步看

  1. 重現：輸入固定是 80、85、88，每次執行都印出 84.00，和預期的 84.33 不同。這支程式用 -Wall -Wextra -Wpedantic 編譯沒有任何警告。
  2. 縮小範圍：在計算後面暫時加一行 printf("總和=%d\n", q1 + q2 + q3);，印出 253，總和是對的，所以問題在除法。
  3. 找出原因：(q1 + q2 + q3) / 3 兩邊都是整數，是整數除法，小數在存進 average 之前就被捨去了（第 3 週，GNU C 手冊 §6.5）。
  4. 修正：改成 (q1 + q2 + q3) / 3.0。

修正後的檔名 avg_fixed.c：

#include <stdio.h>

int main(void)
{
    int q1 = 80;
    int q2 = 85;
    int q3 = 88;

    double average = (q1 + q2 + q3) / 3.0;
    printf("平均：%.2f\n", average);
    return 0;
}

再測試的輸出：

平均：84.33
  1. 再測試：再換一組剛好整除的分數（例如 90、90、90）確認結果仍是 90.00，確保修正沒有造成新的問題。

補充範例 3-2：用 printf 追蹤迴圈

症狀：想加總陣列中的 5 個數字 {4, 7, 1, 9, 3}，答案應該是 24，程式卻印出 20。

檔名 loop_bug.c：

#include <stdio.h>

int main(void)
{
    int values[5] = {4, 7, 1, 9, 3};
    int sum = 0;

    for (int i = 1; i < 5; i++) {
        printf("[除錯] i=%d, values[i]=%d\n", i, values[i]);   /* 暫時加入 */
        sum = sum + values[i];
    }
    printf("總和：%d\n", sum);
    return 0;
}

加入追蹤訊息後的輸出：

[除錯] i=1, values[i]=7
[除錯] i=2, values[i]=1
[除錯] i=3, values[i]=9
[除錯] i=4, values[i]=3
總和：20

一步一步看

  1. 追蹤訊息顯示 i 從 1 開始，第一格 values[0] 的 4 從來沒有被加進去。24 減 4 剛好是 20，和症狀吻合。
  2. 原因是迴圈起始寫成 int i = 1。陣列的索引從 0 開始（第 8 週，GNU C 手冊 §16.1）。
  3. 修正：改成 int i = 0，重新執行確認總和是 24。
  4. 確認修好之後，把 [除錯] 那一行刪掉，避免正式的輸出中出現除錯訊息。

補充範例 3-3：用 assert 讓錯誤提早現形

教材怎麼說：assert(條件) 用來表達「我假設這個條件一定成立」。如果條件不成立，程式會立刻以「assertion 失敗」結束。它通常在除錯期間使用，用來確保沒有發生預料之外的狀況；在 #include <assert.h> 之前定義 NDEBUG，assert 就不會發生作用。出處：Beej 函式庫參考 §3.1、§3.2 assert()。

檔名 use_assert.c：

#include <stdio.h>
#include <assert.h>

double average(int total, int count);

int main(void)
{
    printf("平均：%.2f\n", average(253, 3));
    printf("平均：%.2f\n", average(0, 0));
    printf("這一行不會被執行\n");
    return 0;
}

double average(int total, int count)
{
    assert(count > 0);
    return (double)total / count;
}

執行時，螢幕上會看到類似下面的內容，然後程式立刻結束（assert 的訊息格式依系統而不同）：

平均：84.33
Assertion failed: (count > 0), function average, file use_assert.c, line 16.

一步一步看

  1. 第一次呼叫 average(253, 3)，count > 0 成立，正常回傳 84.33。
  2. 第二次呼叫 average(0, 0)，count > 0 不成立，程式在 assert 那一行立刻停止，並指出是哪個條件、在哪個函式、哪一行失敗。
  3. 如果沒有 assert，除以 0 的問題可能要到後面才以奇怪的數值出現，很難追查。assert 讓錯誤在最接近原因的地方現形。
  4. assert 是用來抓「寫程式的人的錯誤」。使用者輸入錯誤這類可以預期的狀況，仍然要用 if 檢查並給出友善的提示（第 4、5 週）。

動手改改看

  • 補充範例 3-2 中，如果把迴圈條件寫成 i <= 5，會發生什麼事？這種錯誤編譯器一定會警告嗎？（對照第 8 週第 4 節與 cppreference 的說明。）
  • 在補充範例 3-3 的第一行加上 #define NDEBUG，重新編譯執行，比較結果。
