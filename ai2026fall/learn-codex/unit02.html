01先認識幾個名詞

這一頁會用到不少電腦與程式的名詞，先用生活化的方式講清楚，後面讀起來會輕鬆很多。不必一次背起來，看到不懂的詞再回來查就好。後半這幾個詞，接下來三個單元也會一直出現。

檔案與資料夾
檔案是一份資料（一篇文件、一張圖、一個程式）；資料夾是裝檔案的容器，資料夾裡還可以有資料夾。
路徑（path）
檔案在電腦裡的「地址」，例如 專題/程式/main.py 表示「專題」資料夾裡的「程式」資料夾裡的 main.py。
程式碼（code）
用程式語言寫給電腦執行的指示。副檔名常透露它是哪種語言，例如 .py 是 Python，.js 是 JavaScript，.html 是網頁。
終端機（terminal）
一個用「打字下指令」操作電腦的視窗。在圖形介面裡你用滑鼠點「開啟」，在終端機裡你輸入一行指令讓電腦做同樣的事。macOS 叫「終端機」，Windows 常用「PowerShell」。
Bug
程式中的錯誤，讓程式的結果和預期不一樣，或直接當掉。
測試（test）
另外寫一小段程式，自動檢查「輸入這些資料時，結果是不是我們預期的」。每次修改後跑一次測試，就知道有沒有改壞東西。
Git
記錄檔案每一次變化的工具，像是遊戲的「存檔點」。改壞了可以回到之前的存檔。
Commit
在 Git 裡建立一個存檔點的動作，會記下「這個時間點所有檔案的樣子」和一句說明。
專案
一件持續進行的工作，以及它用到的檔案、規則與對話。在 Codex 裡，專案通常對應到電腦上的一個資料夾。
儲存庫（repository）
被 Git 記錄的資料夾，常簡稱 repo。執行過 git init 的資料夾就是一個儲存庫。
分支（branch）
同一個專案的「平行版本」。可以在新分支上嘗試新功能，不影響主要版本（常叫 main），確定沒問題再合併回去。
Worktree
同一個儲存庫在電腦上的另一份工作副本。兩份副本共用 Git 的紀錄，但檔案各自獨立，所以可以同時在兩邊做不同的修改。
設定檔
存放「偏好與選項」的文字檔。Codex 的設定檔叫 config.toml。
技能（skill）
一個資料夾，裡面寫好「某件事該怎麼做」的步驟與參考資料。Codex 讀了它，就能照同一套流程把事情做好。
VS Code
免費的程式編輯器，可以看檔案、改程式、開終端機，也能安裝擴充套件增加功能。
擴充套件
替 VS Code 加上新功能的外掛。Codex 擴充套件讓你在 VS Code 裡直接使用 Codex。
命令選擇區
VS Code 裡用打字找功能的搜尋框（Command Palette）。按 Cmd+Shift+P（macOS）或 Ctrl+Shift+P（Windows）開啟。
CSV
用逗號分隔欄位的表格文字檔，第一行通常是欄位名稱。可以用 Excel 開啟。
JSON
一種常見的資料格式，用 { } 包住一筆資料的各個欄位，用 [ ] 包住一串資料。
函式（function）
一段有名字、可以重複使用的程式。把資料交給它，它算出結果交回來。
測試（test）
自動檢查程式結果是否符合預期的程式。

在哪裡使用 Codex

打開終端機

安裝 CLI 或執行程式時需要終端機：

  • macOS：按 Cmd+Space 開啟 Spotlight，輸入「終端機」或「Terminal」後按 Enter。
  • Windows：按開始鍵，輸入「PowerShell」後按 Enter。

終端機打開後會看到一行提示符號（例如 % 或 >），在後面輸入指令、按 Enter 執行。

安裝 Codex CLI（選一種方式即可）

這些指令在做什麼
  • curl：從網址下載內容。| 叫做管線，把前面下載到的內容交給後面的程式執行。
  • npm install -g：用 Node.js 的套件管理工具安裝，-g 表示安裝成整台電腦都能用的指令。

從網路下載並執行程式前，一定要確認網址是官方來源。

安裝好之後，用終端機進到專案資料夾，輸入 codex 啟動。第一次使用時選擇 Sign in with ChatGPT 登入。Codex 會把你啟動它時所在的資料夾當成這次工作的專案。

cd 是 change directory（切換資料夾）的縮寫，後面接要進去的資料夾路徑。

03Codex 專案是什麼

不同介面怎麼決定「專案」

介面專案是什麼開始方式
ChatGPT 桌面版Projects 畫面中的專案，可以連結電腦上的一個或多個資料夾建立專案，或開啟一個資料夾
Codex CLI啟動 codex 時所在的資料夾在該資料夾執行 codex，或用 --cd <資料夾>（簡寫 -C）指定
VS Code 擴充套件VS Code 目前開啟的資料夾或工作區用 VS Code 開啟資料夾；同時開多個資料夾時，要為對話選擇其中一個作為根目錄

換句話說：你在哪個資料夾打開 Codex，Codex 就在那個資料夾工作。CLI 和 VS Code 擴充套件看不到網頁版或桌面版的 Projects 畫面，所以長期有效的規則要寫在資料夾裡的 AGENTS.md（第 5 節），未來的新對話才讀得到。

什麼時候建立專案

  • 建立專案：工作會持續一段時間、會產出不只一份成果，或會反覆用到同一批檔案。
  • 直接開新對話：一次性的工作，不需要共用檔案、指示或資料夾。
  • 每個成果一個對話：同一個專案裡，「修 bug」、「加新功能」、「寫說明文件」各開一個對話，讓每個對話保持聚焦。

桌面版：一個專案連結多個資料夾

當 Codex 需要讀取或修改電腦上的檔案時，就在桌面版建立本機專案：

  1. 開啟專案選單，選擇 Edit project。

  2. 選擇 Add folder 加入資料夾，可以加入多個。Codex 能讀取和修改每個加入的資料夾。

  3. 在某個資料夾上選擇 Make primary，設為主要資料夾。

主要資料夾有特別的地位：

  • 新對話從主要資料夾開始。
  • Git 操作預設作用在主要資料夾。
  • Codex 只會在主要資料夾自動尋找 AGENTS.md、技能與 config.toml。其他資料夾仍然可以搜尋、讀取、編輯，但這些專案檔不會自動載入。

彼此無關的工作，或希望對話只能碰到其中一部分時，就建立不同的專案。

專案不是安全圍籬

專案與 worktree 負責「整理工作」。真正限制 Codex 執行的指令能讀寫哪些檔案、能不能連網的，是沙箱，也就是下一節的主題。

整理專案與對話

動作用途
釘選專案讓常用專案固定在側邊欄上方
釘選對話常回來看的對話不會被新對話擠下去
重新命名對話用描述成果的短標題，例如「成績報告：資料驗證」
搜尋在 Projects 畫面搜尋專案；記得片段文字或分支名稱時，用 Search chats 找舊對話
封存對話完成後封存；也可以從專案選單一次封存該專案的所有對話

釘選只改變顯示的位置，不會讓 Codex 多知道什麼，也不會改變它能存取的內容。桌面版封存的對話可以從 Settings > Archived chats 還原。在 CLI 中，用 /new 開新對話，用 /resume 或 codex resume 接續舊對話。

04先設好安全網

Codex 會讀檔案、改檔案、執行指令。為了確保一切在你的掌控之中，有兩個機制一起運作：

沙箱（Sandbox）

像是一道圍籬，技術上限制 Codex 能碰哪些檔案、能不能連網。Codex 執行的其他工具（例如 Git、測試工具）也都在圍籬內。

核准（Approvals）

決定 Codex 什麼時候要停下來問你。例如要跨出圍籬時，先徵求你同意。

大多數情況建議使用 Ask for approval 模式：Codex 可以在目前的專案資料夾內自由工作，要超出範圍時會先暫停問你。在 CLI 中輸入 /permissions 可以查看和切換模式。

用 Git 建立存檔點

每次請 Codex 動手前後，都建立一個 Git 存檔點。如果結果不滿意，就能回到修改前的狀態。第一次在一個資料夾使用 Git 時：

逐行解說
  • git init：讓 Git 開始記錄這個資料夾。每個資料夾只需要做一次。
  • git add -A：把「所有檔案目前的樣子」放進準備存檔的區域。-A 代表全部。
  • git commit -m "..."：正式建立存檔點，-m 後面引號裡是這個存檔點的說明，寫給未來的自己看。

之後每次要存檔，只需要執行後面兩行。第一次使用 Git 時，它可能會要求你先設定姓名與 email，照畫面提示輸入即可。

  • git status：列出哪些檔案被改過。
  • git diff：逐行顯示改了哪些內容，- 開頭是刪掉的行，+ 開頭是新增的行。
  • git restore .：放棄所有還沒存檔的修改，回到上一個存檔點。這個動作無法復原，執行前先用 git diff 確認。

05把專案規則寫進專案

每次請 Codex 做事，你可能都要重複交代「修改後要跑測試」、「不要改原始資料」。把這些規則寫成檔案放進專案資料夾，Codex 開始工作前會自動讀取，就不用每次重講。一個「交給任何人打開都能順利工作」的 Codex 專案，通常長這樣。以 . 開頭的資料夾在 macOS 的 Finder 和 Windows 檔案總管中預設會隱藏，但在 VS Code 的檔案總管裡看得到。

Markdown 是什麼

.md 結尾的檔案是 Markdown 格式，一種用簡單符號標示格式的純文字檔：

  • # 標題：一個 # 是大標題，## 是小一級的標題。
  • - 項目：減號加空格開頭，是條列項目。
  • `文字`：用反引號包起來，表示這是指令或程式名稱。

範例：畢業專題的 AGENTS.md

這五條規則有三種類型：做完要驗證什麼、做之前要先問、不准碰哪裡。自己寫規則時，照這三個方向想就對了。

Codex 怎麼找 AGENTS.md

Codex 每次開始工作時，會把找到的規則檔串成一份指示：

  1. 全域：Codex 家目錄（預設是 ~/.codex）裡的 AGENTS.override.md；沒有的話讀 AGENTS.md。這是你個人套用到所有專案的規則。（~ 代表你的使用者家目錄。）

  2. 專案：從專案最上層（通常是 Git 儲存庫的根目錄）一路往下，走到你目前所在的資料夾。每一層依序找 AGENTS.override.md、AGENTS.md，每層最多採用一個。

  3. 合併：由上往下串起來。越靠近目前資料夾的檔案越晚出現，所以會覆蓋前面的規則。

用例子看懂「越近越優先」

如果在 bookshop/backend/payments 裡啟動 Codex，它會依序讀到三份規則。「繁體中文」照樣適用；但測試指令的規則，付款模組那份最靠近，所以以「make test-payments」為準。

還要注意：

  • 空白的規則檔會被略過。所有規則合併後的大小上限預設為 32 KiB（約一萬多個中文字），超過就不再加入。專案很大時，把規則拆到各子資料夾。
  • 在要放規則的資料夾執行 /init，Codex 會產生一份 AGENTS.md 草稿，檢查、修改後再 commit。
  • 想確認 Codex 讀到了哪些規則，直接問它：「列出你載入的指示來源。」

成績報告範例（第 4 單元）的 AGENTS.md：

.codex/config.toml：專案層級設定

個人預設設定放在 ~/.codex/config.toml；某個專案需要不同的設定時，在專案中加入 .codex/config.toml。CLI 與 VS Code 擴充套件共用同一套設定。

TOML 格式很單純：每一行寫「設定名稱 = 值」，文字值要加引號，# 後面是註解（給人看的說明，Codex 會忽略）。

同一個設定可能出現在好幾個地方，Codex 依下面的順序決定用哪一個（數字越小越優先）：

順序設定來源
1啟動 CLI 時直接加的旗標與 --config 覆寫
2專案的 .codex/config.toml（越靠近目前資料夾越優先，只在信任的專案生效）
3用 --profile 選擇的設定檔
4你的使用者設定 ~/.codex/config.toml
5工作區雲端管理的預設值
6系統設定（Unix 為 /etc/codex/config.toml）
7Codex 內建的預設值
安全提醒
  • 把專案標記為不信任時，Codex 會略過專案裡的 .codex/ 設定，包括專案設定、hooks 與 rules。從網路下載的陌生專案，先確認內容再信任。
  • 專案設定檔不能改和帳號憑證、服務供應商、設定檔選擇有關的設定（例如 model_provider、profile），Codex 會忽略並在啟動時警告。
  • 在 CLI 中執行 /status 可以看目前的模型、核准政策與可寫入路徑；/debug-config 會依優先順序列出各設定層。

06技能：把重複的做法打包起來

如果你常常要 Codex 做同一件事（例如「跑完所有檢查並整理結果」），每次都貼一大段提示很麻煩，也容易漏掉步驟。技能就是把這套做法寫成檔案，放在專案裡，需要時一句話叫出來。

技能的組成

技能是一個資料夾，裡面一定要有 SKILL.md，可以另外附上 scripts/（程式）、references/（參考文件）、assets/（範本或資源）。SKILL.md 開頭兩條 --- 之間必須寫 name（名稱）與 description（什麼時候用）：

Codex 怎麼使用技能

  • 明確呼叫：在 CLI 或 VS Code 擴充套件輸入 $ 接技能名稱，例如 $grade-report，或執行 /skills 選擇。
  • 自動選用：你的請求符合技能的 description 時，Codex 會自己選用。所以描述要精簡，把關鍵用途和觸發字放在前面。
  • 用到才細讀：Codex 一開始只看每個技能的名稱與描述，決定使用某個技能時，才讀完整的 SKILL.md。

技能放在哪裡

範圍位置適合放
REPO從目前資料夾往上到儲存庫根目錄，每一層的 .agents/skills跟這個專案有關的技能，隨專案一起 commit 分享給組員
USER$HOME/.agents/skills你個人在任何專案都會用到的技能
ADMIN/etc/codex/skills整台機器共用的預設技能
SYSTEMCodex 內建例如 skill-creator、plan

建立技能

  • 輸入 $skill-creator，Codex 會問你這個技能要做什麼、什麼時候觸發，然後幫你產生草稿。
  • 也可以手動建立資料夾和 SKILL.md。Codex 會自動偵測技能變更；沒出現的話，重新啟動 Codex。
寫好技能的四個原則
  1. 一個技能只做一件事。
  2. 除非需要每次都得到完全相同的結果，或需要外部工具，否則優先用文字說明步驟。
  3. 步驟寫成明確的命令句。
  4. 寫清楚輸入是什麼、輸出是什麼。

07動手看一次：Codex 修好一個有錯的程式

這一節用一個很小的 Python 程式，完整走一遍「發現錯誤、請 Codex 修、檢查結果」的過程。就算你從來沒寫過程式，也能照著看懂每一步發生了什麼事。

下載本節範例：平均分數程式

第 1 步：看懂這個程式想做什麼

這個程式想計算一串分數的平均。平均的算法是：把所有分數加起來，再除以分數的個數。

逐行解說
行號程式碼的意思
1def average(scores): 定義一個叫 average 的函式。函式像一台機器：把資料（這裡叫 scores，一串分數）放進去，它會算出結果。冒號後面縮排的幾行，都是這台機器的內部步驟。
2total = 0 建立一個叫 total 的變數，先放入 0。變數像一個貼了標籤的盒子，用來暫存數字。
3for score in scores: 迴圈：從分數串列中一次拿出一個分數，叫它 score，對每個分數都執行下一行。
4total = total + score 把目前的總和加上這個分數，再存回 total。迴圈跑完，total 就是全部分數的總和。
5return total / 3 把總和除以 3，當成結果交回去。問題就在這裡。
8-10print(...) 把結果顯示在畫面上。[80, 90, 70] 是一個有三個分數的串列，[] 是一個空的串列。

第 2 步：執行，發現結果不對

逐一檢查：

  • 80、90、70 的平均是 80，正確。
  • 100、60 的平均應該是 80，程式卻算出 53.33，錯誤。因為程式固定除以 3，但這裡只有 2 個分數。
  • 沒有任何分數時，程式回答 0.0。但「沒有分數」不等於「平均 0 分」，這個結果會誤導人。
觀察重點

第一個例子剛好是 3 個分數，所以結果看起來正確。只測一種情況，很容易漏掉錯誤，這就是為什麼需要多種情況的測試。

第 3 步：把問題描述清楚，交給 Codex

在 average-bug 資料夾中啟動 Codex（或在桌面版、VS Code 開啟這個資料夾），輸入：

為什麼要這樣寫提示？
  • 重現方式：給出「怎麼執行、看到什麼、預期什麼」，Codex 可以自己跑一次確認問題，比「平均算錯了」精確得多。
  • 限制：避免 Codex 順手改了其他地方，讓你難以檢查。
  • 驗證方式：要求它修完後再執行、加測試、回報結果，你不用盲目相信「我修好了」。

第 4 步：看 Codex 改了什麼

Codex 會顯示它修改的內容（稱為 diff）。下面是一份參考解答，Codex 實際的寫法可能略有不同，但重點一樣：

改了哪裡、為什麼
  • + 開頭是新增的行，- 開頭是刪掉的行，前面是空格的行沒有變。
  • 第 2 行三個引號包起來的文字是說明文字，寫給閱讀程式的人看，不影響執行。
  • 第 3-4 行：len(scores) 是串列裡有幾個分數。如果是 0 個，就直接回傳 None（Python 裡代表「沒有值」），不往下算。
  • 第 8 行：除以 len(scores)，也就是「實際的分數個數」，不再固定除以 3。

第 5 步：用測試確認真的修好了

參考的測試檔如下（Codex 寫的測試名稱或順序可能不同）：

逐行解說
行號程式碼的意思
1載入 Python 內建的測試工具 unittest。
3從 average.py 取出 average 函式來測試。
6建立一組測試，名字叫 AverageTest。
7-8第一個測試：assertEqual 意思是「斷定兩者相等」。算出來的平均必須等於 80，否則測試失敗。
10-11第二個測試：兩個分數的平均也必須是 80。原本的錯誤就會在這裡被抓到。
13-14第三個測試：assertIsNone 斷定沒有分數時結果是 None。
17-18直接執行這個檔案時，跑所有測試。

三個測試都顯示 ok，最後一行是 OK，代表全部通過。以後不管誰修改 average，只要再跑一次測試，就知道有沒有改壞。

試試看

08專題中最常用的 Codex 工作流程

好的 Codex 提示會說清楚四件事：想要的行為、相關的程式或重現步驟、必須保留的限制、如何驗證。下面的例子以一個「校園二手書交易平台」專題為背景，你不需要懂裡面的技術名詞，重點是看提示的結構。

流程 1：看懂別人的程式

接手組員或網路上的程式時，先請 Codex 帶你讀懂。在 VS Code 中打開相關檔案、選取想了解的程式碼，然後問：

再要一份可以核對的整理，方便你自己打開檔案確認：

流程 2：修 bug

和第 7 節動手做的方式一樣：重現步驟比描述問題更有用。

「回歸測試」是專門確認「這個 bug 以後不會再出現」的測試。

流程 3：寫測試

「邊界情況」是最容易出錯的極端輸入，例如 0、最大值、負數、空白。

流程 4：從設計稿做出畫面

設計稿圖片可以直接給 Codex，但框架、互動行為這些圖片看不出來的資訊，要用文字補充。

流程 5：邊看畫面邊微調

先啟動網頁的開發伺服器（會自動重新整理畫面），再用小而具體的提示反覆調整：

喜歡的修改就 commit，不喜歡的就還原。如果你自己改動或還原了某段程式，要告訴 Codex，免得它下一輪把你的修改蓋掉。

流程 6：交作業或合併前做程式碼審查

/review 會列出依嚴重程度排序的問題，不會改動你的程式碼。修正後再跑一次，確認問題解決。專案必須是 Git 儲存庫才能使用。小組若把專案放在 GitHub 並啟用 Codex 程式碼審查，也可以在合併請求（PR）留言 @codex review。

流程 7：大任務先規劃，再設定目標

需求還不明確時，先用 /plan 請 Codex 調查並提出做法：

計畫確定後，用 /goal 設定一個持續進行的目標。好的目標包含三件事：

目標元素要寫什麼範例
成果想要的結果，而不只是活動完成站內訊息的第一階段：一對一文字訊息

10整合演練：一個專題從發想到展示

以「實驗室器材借用系統」為例，看三種工作方式如何接力：

  1. 1 發想Chat：腦力激盪使用情境、比較技術選項
  2. 2 規劃Work：計畫書草稿、時程表、分工試算表
  3. 3 建立專案Codex：/init 產生 AGENTS.md
  4. 4 開發Codex：做畫面、實作功能、寫測試、修 bug
  5. 5 審查Codex：每次合併前 /review
  6. 6 展示Work：期末簡報與展示網站

課堂活動（兩人一組）

  1. 選一個你們想做的專題題目。

  2. 用 Chat 寫一個包含四要素的提示，請 AI 列出 5 個核心功能與可能的風險。

  3. 至少追問兩次，例如：「你做了哪些假設？」、「哪一個功能最可能做不完？為什麼？」

  4. 把結果改寫成給 ChatGPT Work 的提示，要求產出一份專題時程試算表。

  5. 和旁邊的組別交換提示，互相指出缺少了哪一個要素。

11總結與課後練習

五個使用守則

  1. 選對工具：問問題用 Chat，要成品用 Work，碰程式碼用 Codex。

  2. 說清楚：目標、脈絡、產出、界線，用得到的就寫上。

  3. 要驗證：追問來源與假設，親自檢查數字、引用與每一頁內容。

  4. 留退路：Codex 動手前後建立 Git 存檔點，預設使用 Ask for approval。

  5. 守誠信：AI 是幫你學會，不是替你交差；依各課程規定使用並註明。

接下來的單元

第 3 單元在 VS Code 中用擴充套件指令、斜線指令與代理工作階段和 Codex 協作，並認識 worktree 的用途。第 4 單元用「成績報告產生器」做一次完整的練習：說清楚需求、請 Codex 做出最小可行產品，再親手核對每個數字。第 5 單元用「截止日看板」練習 worktree 平行作業、技能重現與整合審查。兩個範例都可以在對應的單元頁直接下載。

課後練習

  1. Chat：挑一個本週課程中最不熟的觀念，用「讓 AI 當家教」的提示對話至少 5 回合，記錄你在哪一回合想通。
  2. 專案：為一門本學期的課建立 ChatGPT 專案，上傳講義並寫好專案指示。
  3. Work：用自己的筆記產出一份考前複習講義或簡報，並列出你檢查時發現的 3 個錯誤或不精確之處。
  4. Codex：下載本單元的範例，照第 7 節的步驟請 Codex 修好 before/average.py，並比較它的修法和 after/average.py 有什麼不同。
  5. 規則：為你自己的一個資料夾寫一份 AGENTS.md，至少各寫一條「做完要驗證什麼」、「做之前要先問」、「不准碰哪裡」。
