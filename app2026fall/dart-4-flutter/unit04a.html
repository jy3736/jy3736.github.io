Unit 4A（補充）：為什麼一定要學物件導向？

Unit 4 學會了 class、建構式和 extends 的寫法。這份補充講義不教新語法，而是用一組「先看問題寫法，再看類別解法」的對照範例回答一個問題：為什麼幾乎所有現代程式語言都把物件導向（OOP）當成標準配備？看完你會知道，類別不是多寫幾行的形式，而是讓程式「守得住規則、加得了功能、測得了、組得起來」的工具。

這份講義你會學到（學會了就打勾，會自動記在這台電腦的瀏覽器裡）

1. 你其實從 Unit 2 就一直在用物件

官方文件對 Dart 的第一句介紹就是：Dart 是物件導向語言，每一個物件都是某個類別做出來的。數字、文字、清單也不例外，所以你才能寫 name.toUpperCase()、scores.sort()：資料和處理它的動作本來就放在一起。

基本範例

  • n.isEven：問數字「你是偶數嗎？」，這個能力是 int 類別提供的。
  • name.toUpperCase()：處理文字的動作都跟著 String 走，不用另外找一個函式。
  • runtimeType：每個物件都知道自己是哪個類別做出來的。

為什麼說它是「標準配備」？

你之後會碰到的主流語言都有類別，而且各平台的框架都是用類別蓋起來的：

語言常見用途你會在哪裡看到類別
DartFlutter 跨平台 APP每一個畫面元件（widget）都是類別
KotlinAndroid APP畫面、資料模型、網路請求
SwiftiOS APP畫面、資料模型
Java、C#企業系統、遊戲（Unity 使用 C#）幾乎所有程式碼都寫在類別裡
Python、TypeScript資料分析、AI、網頁套件提供的模型、元件、資料表

這些語言的寫法細節不同，但背後的想法一樣。在 Dart 學會「為什麼要這樣分」，換語言時只是換一套語法。

2. 痛點一：資料誰都能改 → 封裝

情境：做一個悠遊卡 APP，規則很簡單：餘額不能變負的、一次儲值 1 到 10000 元。先看沒有類別的寫法。

沒有類別：用 Map 存資料

先猜猜看會印出什麼，再點我看執行結果
執行結果
付款後餘額：-50
被直接改掉：99999
{owner: 小明, balance: 99999, balence: 0}

三個問題都不會出現錯誤訊息

餘額變成 -50、被直接改成 99999、鍵名打錯多出 balence：程式全部照常執行，錯誤要等到使用者發現才會被看見。規則寫在函式裡，但沒有任何東西強迫別人一定要走那個函式。

改用類別：資料和規則放在一起

把餘額藏起來，外面只能透過 topUp() 和 pay() 改變它。類別寫在 lib/ 裡，主程式用 import 引用：

先猜猜看會印出什麼，再點我看執行結果
執行結果
付 150 元：失敗
付 35 元：成功
儲值 -50 元：失敗
儲值 200 元：成功
小明的餘額：265
交易紀錄：
  拒絕付款 150（餘額 100）
  付款 -35
  拒絕儲值 -50
  儲值 +200
  • int _balance;：名稱用底線開頭，代表「只有這個檔案裡的程式看得到」。Dart 沒有 private 這個關鍵字，用底線表示。
  • int get balance => _balance;：只給 getter、不給 setter，外面能看不能改。
  • pay() 和 topUp() 是改變餘額的唯一入口，規則只要寫在這裡一次，就不可能被繞過。
  • List.unmodifiable(_history)：交出去的是唯讀副本，外面拿到也改不了真正的紀錄。

試試看：從外面直接改 _balance

錯誤訊息（實際執行結果）
e13_private_field.dart:5:8: Error: The setter '_balance' isn't defined for the type 'IcCard'.
 - 'IcCard' is from 'package:data_lab/unit04a/ic_card.dart' ('lib/unit04a/ic_card.dart').
Try correcting the name to the name of an existing setter, or defining a setter or field named '_balance'.
  card._balance = 99999;
       ^^^^^^^^

在別的檔案裡，_balance 根本「不存在」，所以分析器說找不到這個 setter。這次錯誤在還沒執行時就被抓到了。

注意：底線的保護範圍是「一個檔案」

Dart 的隱私單位是 library，每一個 .dart 檔就是一個 library。如果把類別和 main() 寫在同一個檔案，main() 還是看得到 _balance。這就是為什麼這個範例要把類別放進 lib/ 另一個檔案。在 DartPad 只有一個檔案時，可以先觀察 getter 擋住 setter 的效果。

封裝的好處

規則集中在一個地方：要改「單次儲值上限」只改一行，所有用到悠遊卡的畫面自動跟著變。之後在 Flutter 裡，畫面只負責「顯示餘額、按下付款」，不必知道規則細節。

3. 痛點二：switch 越寫越多 → 多型

情境：結帳時支援多種付款方式，每一種的手續費算法不同。先看用字串分辨款式的寫法。

沒有多型：每個函式都要 switch 一次

先猜猜看會印出什麼，再點我看執行結果
執行結果
現金：付 200 元，手續費 0.0 元
悠遊卡：付 200 元，手續費 0.0 元
行動支付：付 200 元，手續費 2.0 元
未知：付 200 元，手續費 0.0 元
  • 'Mobile' 只是多打一個大寫，程式不會報錯，只會悄悄印出「未知、手續費 0 元」。
  • 每多一種付款方式，feeOf、labelOf 以及所有寫了 switch 的地方都要改。漏改一處就是一個 bug。

改用多型：每種款式自己知道怎麼算

先猜猜看會印出什麼，再點我看執行結果
執行結果
現金：200 元＋手續費 0.0 ＝ 200.0 元
悠遊卡：200 元＋手續費 0.0 ＝ 200.0 元
行動支付：200 元＋手續費 2.0 ＝ 202.0 元
信用卡：200 元＋手續費 4.0 ＝ 204.0 元
信用卡分 3 期：200 元＋手續費 7.0 ＝ 207.0 元
  • checkout() 的參數型別是 List<PaymentMethod>，它只知道「每個東西都有 receipt()」，不知道也不在乎實際是哪一種。
  • 同一行 m.receipt(amount)，遇到不同物件就執行不同的 feeFor()：這就是多型（polymorphism，「同一個呼叫，多種行為」）。
  • CreditCard 是後來才加的，只要多寫一個類別，checkout() 一行都不用改。圖中的虛線框就是新加的部分。
  • 打錯字的問題也消失了：Mobilepay() 不是任何一個類別，分析器會直接標紅。

「對擴充開放、對修改封閉」

好的設計讓你加新功能時只新增程式、不修改舊程式。舊程式沒被動到，就不會被改壞。APP 會一直長新功能，這一點比寫得快更重要。

小練習：新增「禮券」付款方式

在 s05_polymorphism.dart 加上 Voucher 類別：建構式用具名參數 faceValue（面額），手續費 0 元，label 要顯示面額，例如「禮券（面額 500 元）」。完成後確認 checkout() 一個字都沒改。

4. 痛點三：程式綁死在某個資料來源 → 介面

情境：做一個「今天穿什麼」APP，依氣溫給建議。真正的氣溫要上網查，可是你想測「剛好 28 度」「查不到」這些邊界情況，總不能等天氣配合。解法是讓建議程式只依賴一份規格，而不是依賴某個特定的資料來源。

延伸練習

先猜猜看會印出什麼，再點我看執行結果
執行結果
臺南 31.5°C：短袖＋防曬
臺北 24.0°C：薄長袖
嘉義 17.2°C：厚外套
花蓮：查不到氣溫，先帶件外套
--- 換成假資料，專門測邊界值 ---
測試 28.0°C：短袖＋防曬
測試 27.9°C：薄長袖
測試 20.0°C：薄長袖
測試 19.9°C：厚外套
測試：查不到氣溫，先帶件外套
  • abstract class WeatherSource：一份規格，只規定「給城市、回傳氣溫或 null」。
  • implements WeatherSource：保證「我提供這份規格要的每一個方法」，但不繼承任何現成的程式碼。官方文件說明，每個類別都會自動定義一個同名的介面。
  • OutfitAdvisor 只認得 WeatherSource。給它正式來源就是正式版，給它 FakeWeather 就能精準測 28.0、27.9、20.0、19.9 和 null 這幾個邊界值。
寫法意思什麼時候用
extends繼承：接收父類別寫好的程式碼子類別真的「是一種」父類別，而且想共用程式碼
implements實作介面：只承諾提供同樣的方法想換掉實作，例如正式版和測試用的假資料

可以測試，才敢修改

Unit 3 學過寫測試。程式依賴介面以後，測試時就能塞進假資料，不必連網路、不必等天氣。之後 Unit 6 改成真的上網查資料，OutfitAdvisor 也完全不用動。

5. 痛點四：畫面越來越複雜 → 組合

一個 APP 畫面有標題、卡片、文字、按鈕，卡片裡面又有文字和按鈕。如果整個畫面寫成一個大函式，改一張卡片就要在幾百行裡找。OOP 的做法是：每個元件都是一個物件，大元件由小元件組成。

  • Text、Button 是最小的元件，各自知道怎麼畫自己。
  • Column 和 Card 是容器：它們持有其他 Widget，畫的時候請孩子先畫，再排列或加框。它們不在乎孩子是哪一種，因為大家都是 Widget（這裡同時用到了多型）。
  • ScoreCard 自己不畫任何東西，它的 build() 只是把現成元件組合起來。換一位學生，只要換參數。
  • 「A 裡面有 B」（has-a）用組合；「A 是一種 B」（is-a）才用繼承。實務上組合用得比繼承多。

這是模仿，不是真正的 Flutter

範例裡的 Text、Column、Card 是為了說明自己寫的，在終端機印出文字。Flutter 真正的元件名稱很像，但參數和用法不同，學到 Flutter 時以官方文件為準。

Flutter 的畫面就是一棵物件樹

Flutter 的每個元件都是類別的物件，畫面由元件一層一層組合而成。你自己寫的畫面元件也會繼承框架提供的類別，在 build() 裡回傳組合好的元件。看懂這個範例，之後看 Flutter 程式就不會覺得陌生。

6. 綜合實作：飲料店點餐

最後把前面的想法放進同一個小情境：訂單自己守規則（封裝）、各種優惠自己算折扣（多型）、訂單由品項組成（組合），還能自動挑出最划算的優惠。

先猜猜看會印出什麼，再點我看執行結果
執行結果
加入 2 杯珍珠奶茶：true
加入 0 杯紅茶：false
加入 3 杯紅茶：true
原價：210 元
不使用優惠：210 元
全單 9 折：189 元
第二杯半價：165 元
自動選擇「第二杯半價」，應付 165 元
  • 封裝：_lines 藏在 Order 裡，只能用 add() 加入，0 杯或超過 20 杯都會被拒絕。
  • 多型：bestOf() 對每個優惠呼叫同一個 totalWith(d)，不需要知道是打折還是第二杯半價。
  • 組合：Order 有很多 OrderLine，每個 OrderLine 有一個 Drink，各自只算自己的部分。
  • 老闆明天想加「滿 200 折 30」？只要多寫一個 Discount 子類別，放進 options 清單就好。

挑戰題

  1. 新增 FullReduction 優惠：原價滿 200 元折 30 元，未滿不折。Order 一行都不能改。
  2. 想一想：為什麼 Order 不提供一個 lines getter 直接交出 _lines？如果一定要給，應該怎麼寫？（提示：回頭看悠遊卡的 history）

8. OOP 不是萬靈丹：什麼時候不用類別？

Dart 是多範式語言：除了類別，也有獨立的函式、可以當成值傳來傳去的函式，以及 Unit 3 用過的 where、map。物件導向是組織大型程式的骨架，不是每一行都要包成類別。

情況建議
一次性的計算一個函式就好，例如把攝氏轉成華氏
資料有規則要守用類別封裝，例如餘額、庫存、訂單
同一件事有很多種做法用抽象類別＋多型，例如付款方式、優惠
需要換掉實作或測試依賴介面，例如資料來源
東西由小東西組成用組合，例如畫面元件

繼承不要疊太深

繼承層數一多，改父類別就可能牽動一大串子類別。先問自己「這是 is-a 還是 has-a？」，能用組合解決就先用組合。

9. 重點整理

  • Dart 裡放得進變數的東西都是物件，你從第一支程式起就在用 OOP。
  • 封裝：把資料藏起來，只留下守規則的入口，規則就不會被繞過。底線的保護範圍是一個檔案。
  • 多型：同一個呼叫遇到不同物件做不同的事，取代一長串 switch，新增款式不必改舊程式。
  • 介面：依賴規格而不是依賴實作，才能換資料來源、用假資料測試。
  • 組合：大元件由小元件組成，這正是 Flutter 畫面的組成方式。
  • 類別是骨架，不是每件事都要包成類別。

10. 自我檢查

  1. 悠遊卡範例中，如果把 IcCard 類別和 main() 寫在同一個檔案，card._balance = 99999; 還會出錯嗎？為什麼？
  2. s04 和 s05 都能算手續費。要新增「信用卡」時，兩種寫法各要改哪些地方？
  3. FakeWeather 為什麼用 implements 而不是 extends StationWeather？
  4. 「訂單有很多品項」和「信用卡是一種付款方式」，哪一個適合組合、哪一個適合繼承？
看參考答案
  1. 不會出錯。Dart 的隱私單位是 library（一個檔案），同一個檔案裡的程式都看得到底線開頭的名稱。
  2. 沒有多型的 s04 要改 feeOf、labelOf 以及所有其他寫了 switch 的地方；有多型的 s05 只要新增一個 CreditCard 類別，舊程式都不用動。
  3. 假資料不需要正式版的任何程式碼（例如那份固定的氣溫表），只需要提供同樣的 celsiusIn()。只要規格、不要實作時，就用 implements。
  4. 訂單「有」品項，用組合；信用卡「是一種」付款方式，用繼承。
